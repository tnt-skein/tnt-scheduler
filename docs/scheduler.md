# Работы по расписанию

`tnt-scheduler` — работы по расписанию cron в самом узле Tarantool:
«в 03:00 по будням по Москве», «каждый час», «первого числа месяца».
Выражение разбирает рок `cron-parser`, цикл `tnt-loop` остаётся фибером
и тактом, а расписание отвечает только на вопрос, когда следующий такт.

```lua
local jobs = require('tnt.scheduler').new({ zone = 'Europe/Moscow' })

jobs:job('audit-export', '0 3 * * 1-5', export.flush)   -- по будням в 03:00 по Москве
jobs:start()
```

Зависит от [`tnt-loop`](https://github.com/tnt-skein/tnt-loop) (цикл
работы), [`tnt-clock`](https://github.com/tnt-skein/tnt-clock) (часы),
[`tnt-date`](https://github.com/tnt-skein/tnt-date) (смещение пояса),
[`tnt-log`](https://github.com/tnt-skein/tnt-log) (журнал),
[`tnt-must`](https://github.com/tnt-skein/tnt-must) (проверки
аргументов), [`tnt-metrics`](https://github.com/tnt-skein/tnt-metrics)
(ряды запусков и пропусков), [`tnt-external`](https://github.com/tnt-skein/tnt-external)
(подмена часов в проверках) и рока `cron-parser 1.0.0-1` — он приходит
с сервера роков Tarantool и собирается из одного файла C, так что
установке нужен компилятор. Замок кластера приходит аргументом —
функцией `occupy`: подойдёт `lock.occupy` из
[`tnt-lock`](https://github.com/tnt-skein/tnt-lock) либо любая функция
с тем же договором (см. «Замок кластера»).

## Зачем пакет

Снимок на большой арене, вычистка устаревшего, выгрузка журнала — всё
это работы «в 3:00 по будням», а не «раз в пять секунд». Период цикла
такого не скажет, а внешний cron не знает ни какой узел сейчас пишет,
ни что соседний узел ту же работу уже сделал. Пакет держит расписание
в самом узле и делает для этого шесть вещей:

- **Расписание — выражение cron**, и разбирает его рок. Своего разбора
  нет, а там, где рок молча ошибается (восьмеричные числа, склейка полей
  табуляцией, срок только от «сейчас», падение процесса
  на неразобранном выражении), фасад закрывает это сам.
- **Срок — по стенным часам в поясе**, с переводом часов по обе
  стороны: срок в выпавшем весеннем часе не пропадает, а в повторённом
  осеннем наступает один раз.
- **У каждой работы свой цикл.** Долгая работа держит только себя,
  два запуска одной работы на узле разом не идут, а сроки, прошедшие
  за долгий запуск, пропускаются, а не догоняются подряд.
- **Итог — что вернул обработчик**: значение, пара `nil, err` либо
  исключение. Журнал не повторяет одну и ту же беду каждую секунду.
- **Узел для записи и замок кластера.** `writable` пропускает срок
  на реплике, `exclusive` отдаёт срок одному узлу кластера, и замок
  держится не меньше `hold` секунд от захвата — узел, чьи часы
  отстают, не исполнит тот же срок второй раз.
- **Ряды метрик**: запуски по итогу, пропуски по причине, длительность.
  Работа раз в сутки, переставшая запускаться, видна и тому, кто
  не догадался спросить.

## Как пользоваться

```lua
local etcd = require('tnt.etcd.client')
local lock = require('tnt.lock')
local scheduler = require('tnt.scheduler')

-- Замок кластера живёт в хранилище решений (etcd). Продление аренды нужно
-- работе, которая идёт дольше аренды.
lock.configure({ client = etcd.new({ endpoints = { 'http://127.0.0.1:2379' } }), identity = box.info.name })
lock.start()

local jobs = scheduler.new({ occupy = lock.occupy, zone = 'Europe/Moscow' })

-- По будням в 03:00 по Москве, на одном узле кластера и только на узле для записи.
jobs:job('audit-export', '0 3 * * 1-5', function(run)
    return export.flush()
end, { exclusive = true, writable = true })

-- Раз в пять секунд на каждом узле.
jobs:job('heartbeat', '*/5 * * * * *', function()
    heartbeat.touch()
end)

jobs:start()
```

Обработчик получает `{ name, scheduled }` — имя работы и срок, по которому
идёт запуск, в секундах UTC, — и отвечает итогом (см. «Итог обработчика»):
значение или ничего — выполнено, `nil, err` — не удалось. Каждый запуск
идёт в своей области контекста [`tnt-context`](https://github.com/tnt-skein/tnt-context)
с новым `request_id`: её заводит такт цикла, и записи журнала одного
запуска связаны одним опознавателем.

### Что умеет фасад

| Вызов | Что делает |
|---|---|
| `scheduler.new({ occupy, zone })` | планировщик; `occupy` — замок кластера, `zone` — пояс работ по умолчанию |
| `jobs:job(name, expression, handler, opts)` | объявляет работу; на идущем планировщике она запускается сразу |
| `jobs:start()`, `jobs:stop()`, `jobs:running()` | запуск и остановка всех работ |
| `jobs:status()` | состояние работ в порядке объявления |
| `scheduler.parse(expression, zone)` | расписание из данных: `schedule` либо `nil, err` |
| `schedule:next(after)` | ближайший срок строго после мига, секунды UTC |
| `scheduler.DONE`, `FAILED`, `SKIPPED` | итоги срока |
| `scheduler.HOLD` | удержание замка по умолчанию, 10 секунд |

Настройки работы:

| Ключ | Что | Умолчание |
|---|---|---|
| `exclusive` | на срок — один узел кластера, под замком `occupy` | `false` |
| `writable` | только на узле для записи | `false` |
| `hold` | сколько секунд от захвата держать замок; только с `exclusive` | 10 |
| `zone` | пояс этой работы | пояс планировщика, иначе UTC |

Негодный аргумент — исключение на строке вызывающего: имя не по образцу
`^[%w_.%-]+$` (оно уходит в имя фибера и в ключ замка), незнакомый ключ
настроек, работа с тем же именем, `exclusive` без `occupy`, `hold` без
`exclusive`, расписание, которое не разобралось.

### Расписание

Выражение — шесть полей, секунды первыми: `секунда минута час день месяц
день_недели`. Запись crontab из пяти полей получает нулевую секунду
впереди, а слова `@yearly`, `@annually`, `@monthly`, `@weekly`, `@daily`,
`@midnight`, `@hourly` переводятся в шесть полей. Имена дней и месяцев —
в любом регистре (`mon-fri`, `JAN`), `?` в поле дня — то же, что `*`.

```lua
local scheduler = require('tnt.scheduler')

-- Расписание из конфигурации — данные: негодное отказывает парой, а не бросает.
local nightly, err = scheduler.parse('0 3 * * 1-5', 'Europe/Moscow')

nightly:next(1789819200)            --> 1789948800 — понедельник, 21.09.2026 00:00 UTC

scheduler.parse('0 0 24 * * *')     --> nil, 'расписание «0 0 24 * * *» не разобрано: Specified range exceeds maximum'
scheduler.parse('0 0 0 30 2 *')     --> nil, 'у расписания «0 0 0 30 2 *» нет ни одного срока за четыре года'
scheduler.parse('@daily', 'Nowhere/City')
--> nil, 'пояс Nowhere/City не годится: нужно имя из базы часовых поясов либо смещение в минутах'
```

Отказ разбора — слова самого рока: они называют поле и беду («Specified
range exceeds maximum», «Invalid number of fields…»). Срок, которого нет
ни разу за четыре года, — тоже отказ: работа с таким расписанием молча
не шла бы никогда.

**Где рок молча ошибается и что с этим сделано** (сверено запуском на 3.8
с роком `cron-parser 1.0.0-1`):

| У рока | В пакете |
|---|---|
| число поля читается `strtol` с основанием 0: `010` — восьмеричное восемь, `08` — отказ «Unsigned integer parse error» | ведущие нули снимаются до рока: `08` — восемь, `010` — десять |
| поля делятся только пробелом, прочие пробельные знаки выбрасываются из поля: `0\t0 3 * * * *` молча становится «каждый час в минуту 3» | всякий пробельный знак — один пробел |
| полей ровно шесть; запись crontab из пяти — отказ | пять полей — нулевая секунда впереди |
| строка от 256 байт — отказ «must consist of 6 fields», хотя полей шесть | длина проверяется и называется: «длиннее 255 байт» |
| `cron.next` считает срок только от `os.time()` | срок от любого мига: `cron_next` библиотеки рока зовётся напрямую |
| `cron_next` на выражении, которое не разобралось, **роняет процесс** («Bus error», переполнение стека в рекурсии поиска) | выражение разбирается в структуру только после «да» открытого `cron.parse` |
| срока нет четыре года вперёд — `-1`, то есть 1969-12-31 23:59:59, без проверки | пустота и отказ парой |

Что рок понимает не так, как crontab, — и это остаётся:

- **день месяца и день недели сводятся по «и»**, а не по «или»:
  `0 0 0 1 * MON` — первое число, которое к тому же понедельник
  (1 февраля 2027), а не «первое число и каждый понедельник». Зато
  `0 0 0 1-7 * MON` — первый понедельник месяца, чего crontab не умеет;
- **четыре года — горизонт поиска.** 29 февраля с марта 2096 года рок
  не находит (следующее — в 2104-м), и `0 0 0 29 2 MON` (29 февраля
  в понедельник, первое — в 2044-м) отвергается при разборе;
- нет `L`, `W`, `#` и поля года; диапазон дней не заворачивает через
  воскресенье (`FRI-MON` — отказ «Specified range start exceeds range end»).

### Пояс и перевод часов

Рок считает в UTC, а «в 3:00» человек говорит о своих часах. Пояс — имя
из базы часовых поясов либо смещение в минутах, как у `tnt-date`;
умолчание — UTC: местный пояс узла зависит от того, как собран контейнер,
и одно расписание шло бы на двух узлах в разные часы. Пояс планировщика —
умолчание его работ, пояс работы — главнее.

Срок ищется по показаниям часов пояса, а обратно в UTC переводится
смещением, которое у пояса будет в миг срока. Перевод часов разбирается так
(сверено на `Europe/Berlin`, 2026 год):

```lua
local berlin = scheduler.parse('0 30 2 * * *', 'Europe/Berlin')

-- 29 марта часы шагнули с 02:00 на 03:00: 02:30 нет, срок — в 03:30 по новым часам.
berlin:next(1774743000)             --> 1774747800 — 01:30 UTC, 03:30 по Берлину

-- 25 октября 02:30 бывает дважды: срок один, по первым показаниям.
berlin:next(1792887000)             --> 1792888200 — 00:30 UTC, 02:30 летнего времени
```

Срок в выпавшем весеннем часе не пропадает — работа «каждую ночь в 02:30»
иначе раз в год не шла бы вовсе. В повторённом осеннем часе срок один;
но узел, поднявшийся внутри повтора после первого срока, найдёт второй:
`berlin:next(1792890000)` (01:00 UTC, 02:00 зимнего времени) —
`1792891800`, 02:30 зимнего времени.

### Срок и сон

**Наступил ли срок, решают стенные часы** (`clock.realtime`): «в 3:00» — это
их показания. **Спит цикл по времени планировщика**, как всякое ожидание
в Tarantool, и не дольше минуты: проснувшись, такт сверяет срок со
стенными часами заново. Сон на сутки одним куском проспал бы перевод часов
и их уход. Отсюда:

- перевод стенных часов назад откладывает срок до новых показаний;
- перевод вперёд через срок — один запуск на ближайшем такте, не позже
  чем через минуту;
- срок, пропущенный за время простоя узла, **не догоняется**: после
  запуска срок считается от сейчас, как у cron;
- сроки, прошедшие за долгий запуск, **пропускаются**: следующий срок
  считается после запуска, от его конца. Два запуска одной работы на узле
  разом не идут — у каждой работы свой цикл, и такт ждёт запуска.

Поиск срока идёт без уступки: обычное выражение — единицы микросекунд,
редкое сочетание дня месяца и дня недели (`* * * 29 2 MON`) — до половины
миллисекунды (замер на 3.8).

### Итог обработчика

Итог — то, что вернул обработчик, по тому же договору, что у обработчиков
[`tnt-queue`](https://github.com/tnt-skein/tnt-queue)
и [`tnt-event`](https://github.com/tnt-skein/tnt-event):

| Обработчик | Итог срока | Журнал |
|---|---|---|
| вернул значение или ничего — и `false` без причины тоже | `done` | `debug` |
| вернул `nil, err` или `false, err` | `failed`, причина — `tostring(err)` | `warn` |
| бросил исключение | `failed`, причина — текст исключения | `error` со стеком |

```lua
jobs:job('cleanup', '@hourly', function(run)
    local removed, err = sessions.sweep(run.scheduled)

    if removed == nil then
        return nil, err                -- срок не удался; следующий — через час
    end

    return removed
end)
```

**Повтора нет**: следующая попытка — следующий срок. Гарантия — не больше
раза на срок на каждом узле, а с `exclusive` — на весь кластер, с оговоркой
о `hold` ниже. Работе, которой нужна доставка «хотя бы раз», обработчик
отправляет сообщение в очередь `tnt-queue`, а работу делает получатель
очереди — с повтором, отсрочкой и зарытыми.

Обработчик идёт в фоновом файбере цикла, и права у него — права процесса,
а не того, кто объявил работу. В чужой транзакции обработчик не зовётся:
у цикла свой файбер.

### Узел для записи: `writable`

Работа, которая пишет в спейсы, на реплике упала бы на первой же записи.
С `writable = true` срок на узле для чтения (`box.info.ro`) пропускается
с причиной «узел только для чтения». В репликасете это «один узел —
ведущий», в шардированном кластере — «по одному на каждый репликасет»:
вычистка своих данных у каждого шарда своя.

### Замок кластера: `exclusive` и `hold`

С `exclusive = true` срок исполняет один узел кластера: перед запуском
работа берёт замок `occupy('scheduler/<имя>')` — функцию с договором
`occupy(имя) → release | nil, err`, где `release` отпускает замок.
Не взят — срок пропущен с причиной замка («замок занят:
scheduler/audit-export»). Отказ хранилища решений — тоже пропуск:
`tnt-lock` не считает его свободным замком. Узел для чтения проверяется
раньше замка — реплика не отнимает срок у узла, который мог бы его
исполнить.

**Взятый замок держится не меньше `hold` секунд от захвата** (умолчание 10).
Работа, кончившаяся за миллисекунду, иначе отпускала бы замок раньше, чем
до него дойдёт соседний узел, чьи часы отстают на две секунды, — и сосед
исполнил бы тот же срок второй раз. Проверка стыка с настоящим `tnt-lock`
это и показывает: с `hold = 0` опоздавший на две секунды узел выполняет
срок повторно. Отсчёт от захвата, а не от срока: узел, сам пришедший
к сроку поздно, иначе отпустил бы замок сразу. Держатель берёт замок
снова, не отпуская, — у `tnt-lock` захват своего замка удача, — так что
работа чаще чем раз в `hold` секунд остаётся на одном узле.

Замок один на кластер: срок исполняет один узел из всех. Работе, у которой
своё дело в каждом репликасете, — копии, вычистке своих данных шарда —
замок на кластер оставил бы без запуска все репликасеты, кроме успевшего
первым: проигравший срок пропускает, а не ждёт. Такой работе `occupy`
передают обёрткой, которая дописывает к имени замка имя репликасета:

```lua
-- Копия у каждого репликасета своя: замок — на репликасет, а не на кластер.
local replicaset = box.info.replicaset.name

local function occupy(name)
    return lock.occupy(name .. '/' .. replicaset)
end

scheduler.new({ occupy = occupy }):job('backup', '@daily', backup.take, { exclusive = true, writable = true })
--> замок scheduler/backup/storage-001
```

Остановка отпускает замок сразу, если запуск не идёт, а идущий — по его
концу. Работе дольше аренды `tnt-lock` (минута) нужно продление —
`lock.start()`, иначе хранилище отдаст замок соседу посреди запуска.

### Состояние и журнал

```lua
-- Сердцебиение из примера выше после двух сроков.
jobs:status()
--> { running = true, jobs = { ..., {
-->     name = 'heartbeat', expression = '*/5 * * * * *', zone = 'Europe/Moscow',
-->     exclusive = false, writable = false, running = false, held = false,
-->     next_at = 1790732600,
-->     counts = { done = 2, failed = 0, skipped = 0 },
-->     last = { outcome = 'done', scheduled = 1790732595, started = 1790732595.0005, elapsed = 2.96e-06 },
--> } } }
```

`next_at` — следующий срок, секунды UTC; `stalled` — почему его нет;
`running` — идёт ли запуск; `held` — держится ли замок; `hold` — только
у `exclusive`. `last` — последний срок: итог, срок, когда начался, сколько
шёл и причина, если не `done`.

Журнал модуля `tnt.scheduler`: пропуск — `info`, отказ и неотпущенный
замок — `warn`, брошенное исключение, упавший такт и расписание без
следующего срока — `error`.
**Тот же итог с той же причиной подряд — `debug`**: работа раз в секунду
на узле, где замок держит сосед, иначе писала бы строку в секунду. Удачный
запуск — `debug` и конец серии: следующий отказ снова виден.

### Ряды метрик

Работа раз в сутки, переставшая запускаться, видна в `status()` только
тому, кто догадался спросить. Поэтому запуски, пропуски и длительность
лежат и рядами в реестре встроенного `metrics` — прикладными рядами
`tnt-metrics`:

| Ряд | Род | Метки | Что значит |
|---|---|---|---|
| `scheduler_runs_total` | counter | `job_name`, `outcome`: `done`, `failed` | сколько раз работа запускалась |
| `scheduler_skips_total` | counter | `job_name`, `reason`: `running`, `read_only`, `locked` | сколько сроков прошло без запуска |
| `scheduler_run_duration_seconds` | histogram | `job_name` | сколько шёл запуск |

Пропуск считается отдельно от запуска: сосед, держащий замок, — обычная
жизнь работы `exclusive`, а не её отказ. Причина пропуска — слово из трёх,
а не текст отказа: `running` — прежний запуск ещё идёт, `read_only` —
узел для чтения у работы `writable`, `locked` — замок кластера не взят.
Текст замка приходит от чужого кода и был бы меткой без границы; его
видно в `status().last.err` и в журнале.

Длительность — монотонными часами, у удачного и неудачного запуска
одинаково; корзины — от 10 мс до часа: работа бывает и мгновенной,
и выгрузкой на час. Имя работы идёт меткой `job_name`, а не `job`: `job`
Prometheus вешает на каждый ряд цели сам. Потолок работ в ряду — сто:
работа сверх него идёт словом `_other`.

Работа `tick` раз в секунду в выкладке узла через одиннадцать секунд:

```
scheduler_runs_total{outcome="done",job_name="tick",alias="series-001-a"} 11
scheduler_run_duration_seconds_sum{job_name="tick",alias="series-001-a"} 6.7516113631427e-05
scheduler_run_duration_seconds_count{job_name="tick",alias="series-001-a"} 11
```

## Чего пакет не делает

- **Не догоняет пропущенное** — ни за простой узла, ни за долгий запуск.
- **Не повторяет** неудачный срок — это дело очереди.
- **Не прерывает** долгий запуск: файбер без уступки не отменить, а свой
  срок на запуск обманул бы — работа шла бы дальше.
- **Не открывает отрезков трассы**: крюка, в который встал бы
  трассировщик, у планировщика нет; `request_id` в области запуска есть.
- **Не запускает работу по требованию** — такт идёт по расписанию.
- Не знает `L`, `W`, `#`, поля года и шага меньше секунды.

## Чем пришлось поступиться

- **День месяца и день недели — по «и».** Это устройство рока; переписывать
  ради «или» — значит писать свой разбор cron.
- **Горизонт в четыре года.** Редкое сочетание дальше него — отказ при
  разборе, а 29 февраля в 2096–2100 годах — «нет следующего срока»
  в `stalled` и `error` в журнале.
- **`hold` бережёт только от расхождения меньше `hold`.** Узел, чьи часы
  отстают больше, исполнит срок повторно.
- **Обвязка знает устройство рока** — модуль `cron.ccronexpr` и объявления
  ffi, которые рок делает при загрузке. Выпуск закреплён в рокспеке
  (`cron-parser == 1.0.0-1`), подъём — отдельная правка со сверкой заново.
  На master рока (не выпущен) другая библиотека и другая структура
  `cron_expr`: восьмеричные числа, табуляция, пять полей и срок от мига
  там уже исправлены, `-1` вместо отказа — нет.
- **Права процесса** у обработчика — как у всякого фонового цикла.

## Проверки

Проверки лежат в `test/` и идут на luatest: `make test`. Расписание
проверяется настоящим роком: пакет — тонкий слой над ним, и двойник
проверял бы, что мы правильно разговариваем сами с собой. Часы
подменяются двойником через `_set_source`: срок наступает мгновенно,
но там, где наступил бы. Такт зовётся прямо, цикл запускается там, где
нужен он сам: удержание замка, пробуждение, упавший такт, перезапуск
посреди запуска.

- `cron_test.lua` — снятие ведущих нулей, пробельные знаки, пять полей
  и слова, предел длины, отказы рока, срок строго после мига и «срока нет»;
- `schedule_test.lua` — разбор из данных, пояс по имени и смещению,
  перевод часов весной и осенью, срок без дробей;
- `job_test.lua` — срок и сон, итог обработчика, пропуски по причине,
  замок и его удержание, журнал без повторов, область контекста запуска,
  ряды метрик по итогу и причине с корзинами;
- `scheduler_test.lua` — проверки аргументов с местом вызывающего,
  настройки работ, запуск и остановка, `status()`;
- `lock_test.lua` — стык с настоящим `tnt-lock`, по экземпляру замка
  на узел на общем двойнике etcd: один узел исполняет срок, опоздавший
  застаёт замок, без `hold` срок исполняется дважды.

Проверок — 99; покрытие строк — 100 % (336 строк), убитых мутантов —
100 % (281 мутант в пяти модулях). Примеры этого документа прогнаны на Tarantool 3.8
с роком `cron-parser 1.0.0-1`, замок — на etcd 3.5.
